# AGENTS.md

AI のコーディングエージェント向けの、このリポジトリでの約束です（人向けの説明は README.md と docs/）。

## このリポジトリ

Storybook の画面をキャンバスに並べてコメントするレビュー用のアプリです。1 つのリポジトリに次を持ちます。

- `api/` — API（Hono・zod-openapi・inversify。domain / use-case / infrastructure / presenter / di-container / handler の層分け。import の向きは eslint が確かめる）
- `src/` — 画面（React・vite・Tailwind CSS）。`src/features/review/bridge/` は Storybook の iframe に差し込む橋渡し。`.storybook/` と `src/features/*/{pages,components}/*.stories.tsx`・`src/features/*/stories/` は review-canvas 自身の画面の Storybook（docs/development.md「review-canvas 自身の Storybook」）
- `infra/` — CDK（コンストラクト `ReviewCanvas`・そのまま出すアプリ・ワークフローが引き受ける出す用のロールのアプリ `bin/deploy-role.ts`）と、ブランチの Storybook を置くスクリプト
- `bin/` — CLI（`review-canvas.mjs`）と、AI がコメントを読んで返すための MCP サーバー（`review-canvas-mcp.mjs`。依存を持たない JavaScript。docs/ai.md）
- `eslint-rules/` — このリポジトリだけの ESLint ルール。`scripts/` — 開発用のスクリプト（`new-api.mjs`: API の雛形、`check-commit-message.mjs`: コミットメッセージの決まり、`check-issue-text.mjs`: Issue・PR の下書きの検査、`issue-images.mjs`: 下書きの画像を `issue-images` ブランチに置いて埋め込む、`check-app-storybook.mjs`: 自身の画面の Storybook の検査、`stage-story-storybooks.mjs`: 自身の画面の Storybook の動く画面に、サンプルのショップを写す）
- `.claude/skills/fix-review-comments/` — 使う側で AI がコメントを直して返すためのスキル（使う側に写すもの）。`dev-*` はこのリポジトリ自身の開発用のスキル、`.claude/agents/` は領域ごとのレビュー用のサブエージェント（読むだけ）、`.claude/hooks/` は編集のたびに検査を返す hook。`llms.txt` は AI 向けの文書の入口
- `examples/sample-storybook/` — 架空のショップのサンプル Storybook（手元で動かすときに並べる）
- `.github/workflows/publish.yml` — 使う側のリポジトリから呼ぶ再利用ワークフロー。`deploy.yml` — 既定のブランチからスタックを出す（リポジトリの変数で有効にしたときだけ）。`storybook.yml` — push でこのリポジトリのブランチの Storybook を置く（`publish.yml` を呼ぶ。変数で有効にしたときだけ）。`auto-merge-claude.yml` — `.claude/` だけの PR の自動マージ
- `.github/ISSUE_TEMPLATE/`・`.github/pull_request_template.md` — 親 Issue・PR 単位の Issue・不具合と、PR の本文のテンプレート

どこに何を置くか・足すときの順番は [docs/architecture.md](docs/architecture.md)、なぜこの形かは [docs/adr/](docs/adr/README.md) にあります。API を 1 本足すときは、雛形（`pnpm run new:api`）から始めます。

## Issue から PR までの流れ

このリポジトリ自身の開発は、Issue で仕様を決める（スキル `dev-write-issue`）→ 実装（`dev-implement-issue`）→ 多視点レビュー（`dev-multi-perspective-review`）→ PR（`.github/pull_request_template.md`）の順に回します。不具合の直し・1 行の直しも同じで、段を飛ばしません（不具合は Issue の不具合のテンプレートで書き、実装は実装役のサブエージェントに渡し、多視点レビューを通してから PR にする）。仕様は人が決め、AI は実装しながら決めません。push・PR の作成・Issue への投稿は人が頼んだときだけ、マージは人がします。ただし変更が `.claude/` の中だけの PR は、CI が通るとワークフローが自動でマージします（くわしくは [docs/development.md](docs/development.md#issue-から-pr-まで)・[main へのマージ](docs/development.md#main-へのマージ)）。

## 守ること

下は、道具で縛れない決まりです。道具で縛っている決まりは、その下の表にあります（破ると lint・テスト・CI が落ち、メッセージに直し方が出ます）。

- 生成物を手で直さない: `openapi.json`（`pnpm run openapi:generate`）・`src/generated/`（`pnpm run codegen`）・`review-canvas.config.schema.json`（`pnpm run config:schema`）・`.storybook/public/mockServiceWorker.js`（msw の版を上げたら `pnpm exec msw init .storybook/public`）
- 設定ファイルの形は `api/infrastructure/config/review-canvas-config.ts`（zod）が正。API・CDK・置くスクリプトはここから読む
- 使う側に固有の値（組織・リポジトリ・AWS アカウント・Auth0 のテナント・メールのドメイン）を既定値としてコードに書かない。CDK のコンテキスト・環境変数・設定ファイルから受ける
- 例に使う名前・ドメインは架空のもの（`example.com`・`example.co.jp`・山田 太郎・サンプルのショップ）にする
- ワークフローの資格情報（`id-token: write`）を持つジョブで、信頼しないブランチのコードを動かさない（付けてよい場所は下の表で縛る）
- スタックの論理 ID・出力の名前・ワークフローの入力・S3 の置き場の形・コメントの項目は、使う側が頼っているので崩さない（docs/development.md「リリースと互換性」）
- コミットのメッセージは日本語で短く書く
- コメントに書くのは「なぜ・出典・外の制約」だけ。道具で縛れる決まりは、コメントではなく道具に移す

| Issue・PR・コメントの下書きに、150 バイト超の空白の無いリンク・@メンション・★が 1 つでない選択肢の行・手元のパス（`/home/`・`/Users/`・`C:\`・`/tmp/` で始まるもの、`file:///home/…` など。URL のクエリ・フラグメントの中は除く）を入れない。画像を埋め込んだ後に、貼る印を残さない（CI では動かない。投稿の前と、画像を埋め込んだ後に AI が動かす）                                                                                         | `node scripts/check-issue-text.mjs [--posted] <下書き>`                                                     | 「… リンクを含む空白の無い塊が … バイトあります」「@… は GitHub が相手に知らせます」「… ★ を 1 つだけ付けます」「手元のパス（…）があります」「画像を貼る印が残っています」                    |

Claude Code では、編集のたびにそのファイルの eslint・prettier が、手を止める前に変更したファイルの eslint・prettier と tsc が動き、違反が返ります（`.claude/settings.json` の hook。docs/development.md「Claude Code の hook」）。

## 確かめる

```bash
pnpm install
pnpm run validate        # eslint・prettier・tsc・cspell・knip・JSON Schema
pnpm run test:small      # 外につながないテストだけ（Docker なし）
pnpm run docker:up       # medium テストの DynamoDB Local
pnpm run test:coverage   # すべてのテストと、層ごとのカバレッジの下限
pnpm run openapi:check
pnpm --dir infra exec playwright install chromium   # infra:test の撮影のテストが使う（docs/development.md「検証」）
pnpm run infra:validate && pnpm run infra:test
pnpm run build && pnpm run build:bridge && pnpm run build:deployed && pnpm run check:deployed-bundle
```

CDK の組み立ては架空の値で確かめます（docs/development.md「検証」）。AWS へ出す・置くのは人が決めます。
