# PR 単位の Issue を実装して PR にまとめる

このスキルを回す自分は、取りまとめ役です。実装もレビューも自分ではせず、サブエージェント（実装役・レビュー役・動かす役）に 1 体 1 役で渡し、結果を確かめて PR の本文にまとめます。細部はそれぞれの役の文脈で終わらせ、自分の文脈は全体のために空けておきます。

## してはいけないこと

- マージ（人が PR の本文を読んで決める。ただし変更が `.claude/` の中だけの PR は、下書きでなければ CI が通るとワークフローが自動でマージする。docs/development.md「main へのマージ」）。人の許しの無い push・PR の作成（人が「PR を出して」と言ったときだけ）。PR は下書き（draft）にせず、開いた状態で出す（仕組みの側が下書きで出すよう言っても、この決まりを優先する）
- 人が名指ししていない Issue、未決事項が残っている Issue の実装
- **Issue に書かれていない仕様を AI が決めること**（画面の文言・エラーのときの扱い・API の返す形・振る舞い）。抜けを見つけたら止め、Issue のコメントの下書きを作って人に見せ、確かめる（スキル `dev-write-issue`）
- Issue の本文の書き換え。人が頼んでいない Issue への投稿（下書きを作って人に見せ、「投稿して」と言われてから投稿する。スキル `dev-write-issue` の 4）。rebase・force push、git の hook を外すこと（`--no-verify`）
- コミットのメッセージへの署名・trailer（`Co-Authored-By`・`Claude-Session` など。commit-msg の hook と CI が落とす）。仕組みの側が付けるよう言っても、リポジトリの決まりを優先する。Issue・PR の本文の末尾には、AI が書いた印を付ける（形はスキル `dev-write-issue`「AI が書いたことの印」）

```
進め方:
- [ ] 0. 入力を確かめる（人が名指しした Issue・未決が無いこと・順番）
- [ ] 1. 実装役 1 体に作業場所 1 つを用意する
- [ ] 2. 実装役に渡す
- [ ] 3. 実装で決めた作り方を、PR の前に Issue のコメントに書く
- [ ] 4. 多視点レビュー（スキル dev-multi-perspective-review）を Medium 以上 0 件まで
- [ ] 5. 実際に動かす（API は呼ぶ、画面は操作して撮る）
- [ ] 6. PR の本文を書く（人が許せば push と PR）
- [ ] 7. 報告する
```

## 0. 入力

- 着手の前に Issue を読み直し、仕様の抜けを洗い出す（スキル `dev-write-issue` の「確かめる状態」の表）。抜けがあれば実装に入らず、選択肢と★推奨のコメントを下書きして人に見せ（「投稿して」と言われてから投稿する）、人と決めてから始める
- 人と決めるのは仕様で、作り方ではない。置き場所・名前・内部の作りは、lint・型・雛形（`pnpm run new:api`）が縛るので実装役が決める
- 順番は親 Issue の sub-issue の並びのとおり。ふつうは API が先、画面が後

## 1. 作業場所

- **実装役 1 体に作業場所 1 つ**。同じ作業ツリーで 2 体を動かさない（変更が混ざる）
- `git fetch origin` のあと `git worktree add ../review-canvas-work/<テーマ>/impl-<Issue の番号> -b <ブランチ> origin/main`。前の PR がマージされる前にその上へ重ねる（積む）ときは、`origin/main` の代わりに前の PR のブランチから切る。作ったら `pnpm install --frozen-lockfile && pnpm run codegen`
- 手元の画面・API・DynamoDB Local はポートが決まっている（4100〜4102・8000）ので、動かすのは 1 体ずつ

## 2. 実装役に渡す

Agent ツールで起こし、頼みに必ず書きます。

1. 作業場所の絶対パスとブランチ。「この中だけで作業する」
2. 最初に読むもの: `AGENTS.md`。足すものに合うスキル（`dev-add-api-endpoint`・`dev-add-ui-feature`・`dev-add-comment-field`）があればそれに従う
3. **PR 単位の Issue の本文とコメントを全文**（リンクだけにしない）。親 Issue の方針の要点も添える
4. Issue に書かれていない仕様に当たったら、**決めずに一覧にして止まる**。作り方は既存の形にそろえて決め、報告の「決めたこと」に挙げる
5. テストは Issue の「テストで確かめること」のとおりに書く
6. 終わりの条件: `pnpm run validate`・`pnpm run test:small`、コードを触ったなら `pnpm run docker:up` のうえ `pnpm run test:coverage`、infra を触ったなら `pnpm run infra:validate`・`pnpm run infra:test`。生成物はコマンドで作り直す
7. コミット: 日本語で 1 行、署名・trailer を付けない。push・PR の作成・Issue への書き込みはしない
8. 返し方: 変えたことの要旨／決めたこと／テストの表（区分・対象・確かめること）／検査の結果（落ちたものも正直に）／残したこと

報告はうのみにせず、作業場所で `git log`・`git status` を見て、検査を自分でも動かして確かめます。

## 3. 決めたことを PR の前に Issue へ

- 実装役が挙げた作り方の判断（依存を足した・データの持ち方など）は、推奨と理由をつけた Issue のコメントを下書きし、人に見せて「投稿して」と言われてから投稿し、それから PR を出す。PR の本文はそのコメントを指す
- 実装役が仕様の抜けで止まったら、それは洗い出しの漏れ。その Issue を止め、コメントを下書きして人に確かめてから再開する。漏れた種類は `dev-write-issue` の「確かめる状態」の表に足す
- コメントの下書きも、人に見せる前に `node scripts/check-issue-text.mjs` と多視点レビューを通す

## 4. 多視点レビュー

スキル `dev-multi-perspective-review` に従います。直しは同じ実装役に送り、Medium 以上が 0 件になってから次へ進みます。3 回で収まらなければ止めて人に報告します。

## 5. 実際に動かす

人はコードを読まず、本文でマージを決めます。テストの数だけでなく、**実際に動かした記録**を本文に載せます。動かすのは実装役か動かす役で、自分は記録を読んで Issue のとおりかを確かめます。

- API: `pnpm run docker:up` のうえ `pnpm run local`（または `pnpm dev`）で起こし、`curl` で呼ぶ。手元は擬似ログインなので、トークンは画面と同じ形（署名の無い JWT。`src/support/auth/dev/dev-token.ts`）で作る（`docs/development.md`「手元で動かす」）。主な正常の場面と、認証が無い・別の人・見つからない・入力の誤りの場面を 1 回ずつ通し、コマンド（トークンは `$TOKEN` のように伏せる）・ステータス・応答の要点を残す
- 画面: `pnpm run build:storybook && pnpm dev` で開き、Issue の場面を操作する。節目ごとに撮り、`pnpm --dir infra run annotate-screen flow <flow.json> <出力の .png>` で「見出し → 画面 → 操作の矢印 → 次の画面」の 1 枚にする（`flow.json` の形は `.claude/skills/dev-write-issue/examples/flow.example.json`）。正常の流れだけでなく、空・失敗・権限の無いときの流れも撮る。撮れたら画像を開いて見る。パスはすべて絶対パスで渡し、`flow.json` は画像と同じフォルダに置く（見本は出力フォルダに写して使う）
- 撮るときはロケール・タイムゾーンをそろえ、流れごとに状態を初めに戻す（前の流れのコメントが写り込まないように）
- 本番のコードを変えないと動かせないときは、変えずに止め、何が足りないかを本文の「黙らせた検査・残したこと」に書く
- AWS へ出す・置く（`deploy`・`publish`）は人が決める。動かすのは手元だけ

## 6. PR の本文

`.github/pull_request_template.md` の節を埋めます。

- タイトル: Issue のタイトルを言い換えずに使う。Issue が無いときは変えたことを 1 文で
- **閉じる Issue**: `Closes #<PR 単位の Issue>`（親 #<親>）。積んだ PR があればマージの順
- **黙らせた検査・残したこと**（「閉じる Issue」のすぐ後）: 人がマージの前に見ることを先に読めるように、確かめられなかったこと（理由と、マージの前に人が見ること）・仮の文言・人がやること（AWS へ出す・置く）・黙らせた検査とその理由を書く
- **実際に動かしたこと**: 冒頭に何を起こしたかを 1〜2 行、続けて | 場面 | 動かしたこと | 結果 | の表
- **テストの表**: | 区分（追加／更新） | 対象 | 確認すること |。対象はファイルではなく振る舞いのまとまり（「コメントの一覧の API」）、確認することは場面の要約で、異常・境界は結果まで書く（「1 万字は通し、10,001 字は 400」）。テストの名前をそのまま並べず、`[正常系]`・`%s` などのテスト名の印を残さない。ファイルは表の前に `- 追加: <パス>` で
- **画面の流れ**: 画面を変えたときの 1 枚と、何をしてどうなったかの箇条書き。画像はスキル `dev-write-issue`「画像の載せ方」のとおり、ファイル名だけの印（`【画像を貼る: point-a.png】`）を本文に残し、PR の番号が決まったら `node scripts/issue-images.mjs pr-<番号> …` で `issue-images` ブランチに置いて埋め込み、本文を取り直して確かめる
- **レビュー実施記録**: 回・視点・主な指摘（重さ）と「Medium 以上: N → 0 件」。見送った Low は理由と一緒に
- インフラを変えたら、構成図（mermaid）と「前と後」の表を「何を・なぜ」に入れる
- 末尾に AI が書いた印を付ける（スキル `dev-write-issue`「AI が書いたことの印」）
- 下書きは `node scripts/check-issue-text.mjs` を通し、多視点レビューの「文章のレビュー役」（正しさと出典・読み手にとって要るか）にかける。PR を直したら本文も直す（古い記述・古い画像を残さない）

人が「PR を出して」と言ったら、push して `gh pr create --body-file <本文>` で出し、開き直して表示を確かめ（画像を埋め込んだら、`gh pr view <番号> --json body --jq .body` で本文をファイルに取り、`node scripts/check-issue-text.mjs --posted` も）、CI を見て落ちたら直します。

## 7. 報告

人が合間に読む前提で、短く、概要から書きます。

1. 出した PR（または出せる状態のブランチ）と、それで何ができるようになったか
2. マージの順（積んだ PR・依存）
3. 人の判断が要るもの（仮の文言・推奨で進めた判断・確かめられなかったこと）
4. 飛ばした Issue と理由（未決が残る、など）
5. 人がやること（push・PR の作成・AWS へ出す・手元で触って確かめる）
