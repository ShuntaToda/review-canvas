# 人がすぐ決められる Issue を書く

**仕様を決めるのは人、洗い出して選択肢と推奨を出すのは AI** です。AI は実装しながら仕様を決めず、後から PR に書くこともしません。人の手を「Issue で選ぶ」と「PR の本文でマージを決める」の 2 つに絞るために、人が読んですぐ決められる形で書きます。

テンプレートは `.github/ISSUE_TEMPLATE/`（`feature.md`: 親 Issue、`pr-unit.md`: PR 単位の Issue、`bug.md`: 不具合）、見本は `examples/`（このスキルのフォルダの中）です。

## してはいけないこと

- 実装・push・PR の作成（スキル `dev-implement-issue` の仕事。人が PR 単位の Issue を名指しして頼んでから動く）
- Issue の本文の書き換え。論点・人が選んだ結論・変わったことは**コメントで**残す（誰が、いつ、何を決めたかを追えるように。新しく起こす Issue の本文と、印を画像に置き換えることは除く）
- @メンション・人の名前・「確認する人」の列を書くこと（誰をいつ巻き込むかは人が決める）
- 使う側に固有の値（組織・リポジトリ・AWS のアカウント ID・Auth0 のテナント・メールのドメイン）、実在の人・会社の名前、費用・工数・社内の事情を書くこと。例は架空のもの（`example.com`・山田 太郎・サンプルのショップ）にする
- 人が頼んでいない投稿。下書きを見せ、人が「投稿して」と言ってから `gh` で投稿する

```
進め方:
- [ ] 0. 親 Issue が無ければ、下書きする
- [ ] 1. 仕様の根拠を読む
- [ ] 2. 決まっていない点を洗い出す（決まっていることは出典つきで外す）
- [ ] 3. 論点ごとに ★の表と注釈つきの画面を作る
- [ ] 4. 下書きを確かめ、多視点レビューにかけ、人が言ったら投稿する
- [ ] 5. 人の選択を受けて、決まったことをコメントで残す（2〜5 を固まるまで回す）
- [ ] 6. PR 単位の Issue を書く（多視点レビュー → 投稿 → 親の sub-issue につなぐ）
- [ ] 7. 固まったかは人に決めてもらう
```

下書き・画像は、リポジトリの外の作業フォルダ（既定は `../review-canvas-work/<テーマ>/issue/`）に置き、コミットしません。

## 0. 親 Issue が無ければ、下書きする

頼まれた機能に Issue が無ければ、`feature.md` の形で親 Issue を下書きします（何を実現するか・なぜ・受け入れ基準・決まっていること）。論点は本文に書かず、投稿した後のコメントで聞きます（3〜4）。人が「起こして」と言ったら起こします。

```bash
gh issue create --title "[機能] <名前>" --body-file <下書きの .md>
```

## 1. 仕様の根拠を読む

読む順番: 担当の Issue → 親 Issue → 関係する Issue・PR のコメント → 文書（`docs/`・`docs/adr/`・`README.md`）→ 既存のコード。

- 同じ機能を分け合う隣の Issue のコメントも読む。境目がもう決まっていたり、推奨が隣の受け入れ基準とぶつかったりする
- API の振る舞いを言い切る前に、ルートの定義（認証・返すステータス）と `openapi.json` まで確かめる
- 互換に触れるか（API の形・コメントの項目・設定ファイル・スタックの出力と論理 ID・ワークフローの入力）を見る。触れるなら、それ自体を論点にする（`docs/development.md`「リリースと互換性」）
- 人がリンクを貼ったら、まずそれを開く。読めなかったものは「読めなかった根拠」として表の上に書き、決まっているかを言い切らない

## 2. 決まっていない点を洗い出す

- 拾う所: Issue の未決の欄、**根拠どうしの隙間**（API の契約と文書の差、どの Issue も受け持っていない範囲）、**API と画面の境目**（決めずに進めると両方で手戻りになるので、いちばん先に）
- 論点に立てる前に、閉じた Issue・決まったことのコメント・ADR を検索する。立てた論点が実はもう決まっていた、がよく起きる
- 決まっていることは「決まっていること」の表に、**1 行ずつ出典**（Issue・PR のコメントのリンク、文書の節、ADR の番号、短い SHA で固定したコードの行）を付けて並べ、論点から外す
- Issue の本文と今の根拠がずれていたら、黙って読み替えず「本文から読み替えること」の表に、読み替えと根拠を書く
- 書き手と読み手で意味がずれやすい言葉（「確認待ち」と「解決済み」など）は、「言葉」に 1 回だけ定義する
- 頼まれていない仕様を足さない。足したいなら選択肢として聞く
- 画面の論点は、**状態を 1 つずつ**洗い出す。デザインやモックにある状態だけでは足りない

  | 確かめる状態                                                         | 例（review-canvas の画面で）                           |
  | -------------------------------------------------------------------- | ------------------------------------------------------ |
  | 開いたとき・読み込み中・空・失敗・やり直し中                         | 未解決のコメントが 0 件の一覧、読み直しに失敗したとき  |
  | 読み込み中・失敗・空になったときに、入力済みの値と画面がどうなるか   | 書きかけの返信があるときに、読み直しが失敗した         |
  | API が 400・401・403・404 にする場面のうち、画面の文言が無いもの     | 書いた本人でない人が編集を押したとき                   |
  | 表示の形が決まっていない値                                           | 日時を相対（3 分前）で出すか、日付で出すか             |
  | 必須・任意の印を出すか                                               | 返信の欄の【必須】                                     |
  | 前後送り・絞り込み・戻るの後に、どの画面・どのスレッドになるか       | 絞り込みを変えた後の J / K                             |
  | 新しく足す入力欄の誤りの文言と、確かめる時点（離れたとき・送るとき） | 空の返信を送ったとき                                   |
  | 知らせを出す時点と消す時点、2 つの知らせが同時に出る場面             | 「確認待ち」に変わった知らせと読み直しの失敗           |
  | キーボードだけ・日本語の変換中の操作                                 | 変換中の Esc・Ctrl/⌘ + Enter                           |
  | 幅・ブランチ・Storybook を替えたときに、入力中の値と表示がどうなるか | 書きかけの返信がある状態でブランチを替えたとき         |
  | 直さない既知の制約                                                   | 画像の画面と動く画面の高さが違うときは、ピンを置かない |

## 3. 論点ごとに ★の表と注釈つきの画面を作る

下書きは会話に流さず、md で作ります。組み立ては見本 `examples/issue-comment.example.md` のとおりです（見出し `## <テーマ>で決めたいこと（日付）` → 「推奨どおりなら 👍、別案なら `a2` のように記号で」 → 言葉 → 決まっていること → 本文から読み替えること → 決めたいこと → あわせて推奨どおりにすること）。

| 決まり                                                                       | 理由                                                                   |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 論点ごとに小さな表に分ける（`#### a　論点名`・見出しの行・その論点の 1 行）  | 大きな表 1 つだと、横に長い行を読みながら画像を探すことになる          |
| 選択肢は必ず入れ、推奨に ★ を 1 つ付け、記号（a1・a2）を振る                 | 読み手は「推奨でよいか」だけを判断でき、返事が 👍 か `a2` の一言で済む |
| 推奨理由の列には理由だけを書く                                               | 「どの PR でやるか」などの段取りが混ざると、判断の材料が埋もれる       |
| 2 回目からは記号を重ねない（前が a〜f なら g から）。見出しに日付を入れる    | 「a2」がどのコメントの a か分からなくなるのを防ぐ                      |
| 論点にするほどでない推奨は、表の下に「あわせて、次のとおりにします」と並べる | 人は違和感があるときだけ返事をすればよい                               |

### 論点ごとに、注釈つきの画面をすぐ横に置く

表だけでは、どの画面のどこの話かが浮かばず、確かめるのに時間がかかります。**画面に関わる論点には、1 論点に 1 枚**、注釈つきの画面を作り、その論点の表のすぐ下に置きます。

- 1 枚に入れるもの: 上に「論点 a　論点名」と何を撮ったか、左に画面（論点に関わる要素に赤枠と番号。囲むのは 1〜3 か所）、右に番号ごとの説明（「ここで決めたいのは〜」を太字で。画面に出ないことは番号を付けず「（画面に無い）」）と選択肢（推奨は青い枠の ★）。選ぶと無くなる要素には斜線
- 表と画像で同じ番号・記号を使う。文章は表にも書き、画像だけに書かない（検索・引用・読み上げができない）
- 撮るもの: 今の画面があれば最新の main を手元で動かして撮る（`pnpm run build:storybook && pnpm dev`）。部品 1 つならサンプルの Storybook のストーリー。まだ無い画面はモック。状態は撮るときに作る（入力して送る、API の応答をブラウザ側で差し替える）
- 作り方: `pnpm --dir infra run annotate-screen points`（`infra/scripts/annotate-screen.ts`。Playwright は infra の依存）。論点ごとの指定を書いた `.mjs` を渡す。見本は `examples/annotate-spec.example.mjs`（開く画面は同じフォルダの `sample-order-form.html`。架空のサンプルのショップ）。説明も選択肢も書かなければ、赤枠を付けた画面だけになる（不具合の「今の画面」に使う）。ブラウザは、開く画面のオリジンと手元のファイルの外へは通信しない（通すオリジンのリダイレクトで外へ出るのも止める）
- キャンバス（4100）を撮るときは、中の Storybook の iframe のオリジンも通す: コマンドの後ろに `--allow http://localhost:4102`（指定の `.mjs` に `allow: ["http://localhost:4102"]` と書いてもよい）

  ```bash
  # pnpm --dir infra は infra に移ってから動くので、パスはすべて絶対パスで渡す
  pnpm --dir infra run annotate-screen points <開く URL か HTML の絶対パス> <出力フォルダの絶対パス> <指定の .mjs の絶対パス> [論点の記号] [--allow <通すオリジン> …]
  # → <出力フォルダ>/point-<記号>.png
  ```

- **撮れたら必ず画像を開いて見る**。番号が大事な文字を隠していないか、文字が切れていないか、写したい状態が写っているか
- 処理の順・分岐（API の確かめの順など）は、上から順の流れ図にする。GitHub は本文の mermaid を表示するので、画像を置かずに書ける。インフラを変えるなら、構成図と「前と後」の表を付ける

### 画像の載せ方

画像は、画像だけを置くブランチ `issue-images` に AI が push して本文に埋め込みます（人が GitHub の画面で貼る手間を無くすため）。

1. AI は、画像を貼る場所に `【画像を貼る: point-a.png】` のように**ファイル名だけ**の印を残した本文を書く（手元のフォルダ・利用者名を公開の本文に出さない。`check-issue-text.mjs` が `/home/`・`/Users/`・`C:\`・`/tmp/` で始まるパスを見つける）
2. 投稿する Issue・PR の番号が決まったら（新しく起こすなら、先に印のまま起こす）、`scripts/issue-images.mjs` で画像を置き、印を `<img>` に置き換えた本文（`<下書き>.embedded.md`）を作る。置き場は `issue-<番号>`・`pr-<番号>`。印と画像が 1 対 1 でなければ何も push せずに止まる。今の作業ツリー・ブランチには触れない

   ```bash
   node scripts/issue-images.mjs issue-12 <下書きの .md> <point-a.png のパス> <point-b.png のパス>
   ```

3. `<下書き>.embedded.md` を `node scripts/check-issue-text.mjs --posted` で確かめてから投稿する（印のまま投稿していたら、その本文を置き換える）。投稿した後、本文を 1 件だけ取り直して、画像が表示されているかを見る

   ```bash
   gh issue view <番号> --json body --jq .body > <ファイル>                          # Issue の本文
   gh api "repos/{owner}/{repo}/issues/comments/<コメントの id>" --jq .body > <ファイル> # コメント
   gh pr view <番号> --json body --jq .body > <ファイル>                             # PR の本文
   ```

- `issue-images` ブランチは消さない・書き換えない（埋め込んだ画像が切れる）。スクリプトは足すだけで、同じ中身なら push しない
- push できないとき（権限が無い・止められた）は、印のまま投稿し、画像のパスの一覧を会話でだけ人に渡して、GitHub の画面で貼ってもらう

## 4. 下書きを確かめ、多視点レビューにかけ、人が言ったら投稿する

1. 道具で確かめる: `node scripts/check-issue-text.mjs <下書きの .md>`。GitHub でコードの表示に化けるリンク（空白を挟まずに 150 バイトを超える塊）・@メンション・★が 1 つでない選択肢の行を、直し方つきで返す。投稿した後も開き直して表示を見る
2. スキル `dev-multi-perspective-review` の「文章のレビュー役」（正しさと出典・読み手にとって要るか・境目）にかけ、Medium 以上が 0 件になるまで直す。文章だけのときは、公開リポジトリの決まり（実名・会社・固有の値・内部の情報）を「正しさと出典」の役が見る。論点が半分に減ることがよくある
3. 人に下書きを見せ、「投稿して」と言われたら投稿する（`gh issue comment <番号> --body-file <下書き>`）。画像があれば「画像の載せ方」の 2・3 のとおり、埋め込んだ本文を投稿する

置き場所:

| 内容                               | 置き場所                      |
| ---------------------------------- | ----------------------------- |
| 機能の仕様、API と画面をまたぐこと | 親 Issue のコメント           |
| 1 つの PR で閉じること             | PR 単位の Issue（本文で書く） |

## 5. 選択を受けて、決まったことをコメントで残す

人の返事が 👍・`a2` だけでは、後から読む人が何に決まったかを追えません。決まったことを改めてコメントに残します（本文は書き換えない）。

```markdown
## 決まったこと（2026-01-22）

[1/15 の論点](リンク) の a・b は推奨どおり、c は c2 で決まりました。

| 記号 | 決まったこと                     | 出典                     |
| ---- | -------------------------------- | ------------------------ |
| a1   | 解決済みのスレッドは書き出さない | [返事のコメント](リンク) |

### まだ決まっていないこと

- …

### このあと

- #12 の sub-issue として PR 単位の Issue を書く
```

- 項目ごとに出典のリンクを付ける（人の返事のコメント・文書の節・ADR）
- 決めたことに誤りが見つかったら、決まった後でも隠さず選び直しを頼み、コメントで直す
- 方針が変わったら、親にコメントで残し、PR 単位の Issue には変えた理由を一言書く
- 決まるまで止めたくないものは、推奨で仮に決め、後で変わる所を 1 か所に閉じ込める。仮に決めたことも Issue に書き、人が「それで進めてよい」と言ったものだけ実装に回す

## 6. PR 単位の Issue を書く

このリポジトリは小さいので、**親 Issue → PR 単位の Issue の 2 段**にします（機能が大きく、API と画面で PR が分かれても、3 段にこだわらず親の下に並べる）。PR 単位の Issue は、親の本文に並べず、**GitHub の sub-issue でつなぎます**（本文を書き換えないため）。

| 段              | 書くこと                                                                                           | 閉じる条件             |
| --------------- | -------------------------------------------------------------------------------------------------- | ---------------------- |
| 親 Issue        | 何を実現するか・なぜ・受け入れ基準・API と画面をまたぐ決定（論点と決まったことはコメント）         | 受け入れ基準を満たした |
| PR 単位の Issue | このPRで終わっている状態・細かい仕様（返す値・境界・設定の名前・画面の文言）・テストで確かめること | PR のマージ            |

- 決めたことは、影響する作業をすべて含むいちばん下の段に書く（画面にも響くなら親、1 つの PR で閉じるなら PR 単位）
- **画面に出る文言（見出し・ボタン・空のとき・エラー）は PR 単位の Issue で決める**。実装役に決めさせると、レビューで直すことになり高くつく
- API の PR を先に書くときは、画面に効く決めごと（返す形・エラー・端の場面）を、画面の PR 単位の Issue の未決の表へ写してから人に確かめる
- マージの順（ふつうは API が先、画面が後）は sub-issue の並びで示す。sub-issue はマージの順に起こしてつなぐ（つないだ順に並ぶ）。並べ替えは `PATCH .../sub_issues/priority`（`sub_issue_id` と `after_id`／`before_id`）。前の PR に積む（前の PR のブランチから切る）ときは、PR 単位の Issue の冒頭にも書く
- 画像で分かりやすくなるなら、**投稿するときの本文に**印を入れておく（後からコメントで足さない）。API の定義だけ・文書だけのものには付けない
- 親に書いたことは繰り返さず参照する。ファイル名・行番号・ライブラリの内部・lint や型が防ぐことは書かない
- PR 単位の Issue も、投稿の前に 4 の確かめと多視点レビューを通す。人が「起こして」と言ったら起こし、親の sub-issue につなぐ

```bash
gh issue create --title "[PR] <名前>" --body-file <下書きの .md>
# 親の sub-issue につなぐ（sub_issue_id は番号ではなく、Issue の id）
gh api -X POST "repos/{owner}/{repo}/issues/<親の番号>/sub_issues" \
  -F sub_issue_id="$(gh api "repos/{owner}/{repo}/issues/<PR 単位の Issue の番号>" --jq .id)"
```

## 7. 固まったかは人が決める

- 固まったかどうかは、仕様を決める人が判断する。迷っている所は実装に入れない
- 人が「#NN を実装して」と名指ししてから、スキル `dev-implement-issue` で実装に入る。そこからは AI が人に聞かずに PR まで進めるので、仕様（文言・エラーのときの扱い・振る舞い）はこの段で決め切る
- 作り方（置き場所・名前・内部の作り）は、lint・型・テンプレートが縛っているので Issue で確かめない

## AI が書いたことの印

Issue・PR・コメントの本文の末尾には、AI が書いたものだと分かるように、次の 2 行を付けます（コミットのメッセージには付けない。hook と CI が落とす）。PR の本文も同じ形です（スキル `dev-implement-issue`）。

```markdown
---

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```
